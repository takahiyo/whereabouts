# GUI刷新・端末適応計画

更新: 2026-10-04。状態: 計画のみ。ユーザー指定により優先度は低い（P3）。既存バックログU01/U04/U05/U09/U10/U12/U14–16とM04をまとめて設計する。今回の変更は計画書のみ。

## 目的と対象

ワイドPC、一般PC、iPadの縦横・分割表示、スマートフォンで、利用可能な幅を活かす。メニュー・検索・リスト・詳細・編集の操作順、名前、アイコン、保存状態を共通化する。機種ごとの別アプリや固定幅ページは作らず、利用中のブラウザ領域と入力手段に応じて再配置する。

共有D1への書込み仕様・列設定JSON・権限・同期の仕様を変えず、devでフロントから試作する。表示設定の永続化は初期段階ではブラウザ内に限定し、拠点共通設定を更新しない。既存設定の意味の変更が必要なら共有データに関わる別作業として後段へ送る。

## 現状の原因（ソース確認）

| 箇所 | 現在の挙動 | 見直し方針 |
|---|---|---|
| js/layout.js: updateCols | 利用幅800〜1400pxでn=1を強制 | 固定区間による抑制を撤廃し、コンテンツに必要な幅で判断 |
| 同関数: isForceCards | n<=1でもforce-cardsを付ける | グループ配置数と一覧/カード形式を独立させる |
| ui.js: PANEL_MIN_PX=760 | 2グループに必要な幅は標準で1540px（760×2+20） | フル一覧の幅とコンパクト一覧の幅を分けて検証 |
| ui.js: MAX_COLS=3 | 超ワイドでも3グループまで | 上限を固定前提にせず、読める幅・人数・視線移動を実測 |
| styles.css: #board.force-cards | グリッドを1frに固定 | カードでも十分な幅があれば複数列を許可 |
| styles.css: data-cols=1のpanel | 負のmarginと拡張幅で端へ広げる | 共通の余白規則へ整理し、画面外へのはみ出しをなくす |
| ヘッダーの検索・状態filter | JS機能が存在するがCSSで隠れている | メニュー整理と併せて常に発見できる検索入口を設ける |

数値はブラウザのCSS上のボードコンテナ幅。ディスプレイの物理解像度とは異なる。既存の拠点列幅・cardBreakpoint指定、ブラウザ拡大によって現在の結果も変わる。単に800〜1400pxの条件だけを削除しても、1列→カードの結び付きと760px基準が残るため、問題全体は解消しない。

## 共通の操作モデル

1. 「在席 / 予定 / お知らせ / ツール」を全端末で同じ順序・名称にする。
2. 拠点切替と「その他（表示設定・共有・ヘルプ・管理・ログアウト）」を同じ場所の入口から使う。管理は権限を持つ人にだけ表示。
3. 在席の操作列は「検索 → グループ/状態で絞り込み → 表示形式 → 対象者の詳細/更新」。タイトルに隠したグループ操作を明示する。
4. 詳細を開く、状態を選ぶ、戻り時間を指定する、保存結果を確認する、という同じ順序を維持する。ホバーや右クリックだけの操作を作らない。
5. 画面を回転・リサイズしても、選択中の人、検索条件、スクロール位置、未保存の入力を保持する。表示形式を変更しただけでは保存APIを呼ばない。
6. 個人IDがない共有ログインでは自分を推測しない。端末種別によって本人更新と代理更新の権限を変えない。

狭い画面ではナビゲーションを2段または折りたたみに再配置するが、主要機能の名前・順序を維持する。「その他」は全幅で同じ用途に使い、スマホだけ主要機能の名前を変えない。下部ナビを採用するかはプロトタイプで比較し、採用時も同じ4機能にする。

| 操作 | 幅が十分な画面 | 狭い画面 | 共通に保つ点 |
|---|---|---|---|
| 主メニュー | 上部に4機能と拠点・その他 | 上部2段/折りたたみ候補 | 名称、並び、選択状態、権限 |
| 検索/絞り込み | 横並びのツールバー | 検索を表示しfilter詳細を開閉 | 条件、件数、解除、グループ移動 |
| 在席一覧 | テーブル/コンパクト行、複数グループ配置可 | 同じ順番の要約行またはカード | 氏名、状態、戻り時間、更新操作 |
| 詳細/編集 | サイドパネル/中央dialog候補 | 画面内に収まるdialog/シート候補 | 項目名、保存、キャンセル、エラー |
| 管理 | 項目分類を左/上に、編集を右/下に | 同じ分類から順に辿る | データ、権限、未保存確認 |
| お知らせ/ツール | リストと詳細を並置可 | リストから詳細へ遷移 | 並び、戻る操作、既読/公開条件 |

## レイアウトの判断

端末名で分岐せず、次の3つを独立に扱う。

- ページの領域配置: ナビ、検索、コンテンツ、詳細ペイン。
- グループの配置: ボード幅と各グループの読める最小幅から1〜複数列を決定。
- メンバーの表示形式: そのグループの実際の幅と利用者の希望からフル一覧・コンパクト一覧・カードを選ぶ。

「自動 / 一覧 / カード」の表示切替を候補にする。一覧を選んだときに1グループだからという理由でカード化しない。狭い領域の一覧は主要項目を残して詳細へ送るか、テーブル領域内の横スクロールを明示する。必要な項目を読めない幅まで縮めない。

ワイドPCでは単一グループの場合も広い一覧と詳細ペインに領域を使う。複数グループなら読みやすい幅で複数列にする。1列のほうが合理的なデータ量の場合を許容し、「幅が広いなら必ず複数列」という別の強制ルールを作らない。

コンパクトカードの最小幅は320〜400px程度を試作の出発点とし、実際の氏名・状態文字数・操作サイズで決める。フル一覧は有効列の最小幅合計を使う。CSS Gridで配置し、部品内部はcontainer queryを候補にする。未対応環境には通常のmedia queryと縦積みのフォールバックを用意する。[MDN: Container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries)

| CSS上の利用幅（仮の区分） | 初期試作の目安 | 確認する内容 |
|---|---|---|
| 320〜599px | コンパクト1列、詳細を開く | 操作ボタンと入力欄が画面内に収まる |
| 600〜899px | 横並びの要約行、カード2列も比較 | 1列のフル一覧も選べ、カード固定にならない |
| 900〜1199px | コンパクト複数列または一覧＋詳細 | iPad縦横や分割で検索・編集の順序が同じ |
| 1200〜1599px | 複数グループ/広い一覧の比較 | 現行800〜1400pxの抑制を引き継がない |
| 1600〜2560px以上 | 2〜4列以上を内容に応じ試作 | 余白を活かし、横に長すぎる行や読順の混乱を避ける |

この区分は完成仕様の固定ブレークポイントではない。余白・詳細ペイン・文字拡大後の有効幅から調整する。CSSだけで並びを変えてDOM読順とキーボード順を不一致にしない。複数列はグループの順序を明示し、人数差が大きい場合は全員一覧も選べるようにする。

## 見た目・操作部品

- 状態の色・文字、ボタン形状、選択状態、余白、文字サイズ、focus、dialogの重なりを共通トークンへ集約。
- 検索、filter、表示切替、詳細を開くボタン、保存結果、空状態を全画面で同じ部品として扱う。
- 「標準 / 高密度」の候補は情報の余白を調整し、タッチの操作領域を極端に縮めない。iPadでマウス併用しても表示を突然切り替えない。
- ホバーを補助にとどめ、タッチ、マウス、Tab/Enter/Space/Escapeで同じ操作を完了できるようにする。
- 開閉ボタンには開閉状態を伝える。モーダルは初期focus・focus閉じ込め・閉じた後の復帰を一貫させる。[W3C: Disclosure](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)、[W3C: Modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- ソフトキーボード、safe area、短い画面、200%拡大を考慮する。印刷は専用表示を維持する。

## 対応範囲と検証マトリクス

第一対象: WindowsのEdge/Chrome、macOS Safari、iPadOS Safari、iOS Safari、Android Chrome。Firefoxは主要操作を確認。サポートversionは実装着手時点の利用実態とAPI対応状況から決め、「全ての旧ブラウザ対応」とは約束しない。

- 幅: 320 / 360 / 390 / 600 / 768 / 820 / 1024 / 1180 / 1280 / 1400 / 1440 / 1600 / 1920 / 2560 / 3440 CSS px。
- 境界: 実装で決めた各切替境界の−1 / 同値 / ＋1px、800/1400px付近の現行不整合。
- iPad: 縦・横、Split View/ウィンドウ縮小、タッチ＋キーボード/トラックパッド併用。
- データ: 1/2/6グループ、0/1/30/100人、長い日本語名・状態・備考、少ない列/多数列、既存拠点設定。
- 状態: ログイン前、一般/管理者、読取中、空、保存中、通信失敗、filter適用、詳細展開、入力途中でリサイズ。
- 方法: ローカルのAPIモックと匿名fixtureによる画像・操作試験。viewportエミュレーションは実機Safariの代替とはみなさない。

受入条件:

1. ページ全体の意図しない横スクロール・負marginによる欠落がない。必要な表/カレンダー内部のスクロールは明示する。
2. 幅が十分なときに不必要な1列カード表示へ固定されない。1グループでも一覧表示を維持できる。
3. 主要項目と更新ボタンを読め、同じ対象者の更新が全端末で同じ順序で完了する。
4. 主要ナビの名称・順序と権限が一致し、横長画面だけの隠れた機能を作らない。
5. 回転・リサイズ・表示切替で入力、選択、filterを失わず、表示操作による書込みAPI呼出しは0件。
6. 200%拡大、Tab操作、ソフトキーボード使用時にfocus・入力・保存/閉じるが画面外に隠れない。
7. DOM再生成による多重イベント・多重ポーリング・ResizeObserverの連続ループがない。
8. 印刷・共有QR・既存列設定とAPI payloadの互換性を保つ。共有D1を変更せず検証できる。

## 実装時の戻し方

devでGUI版を試験し、mainへマージする前に現行画面との差を確認する。旧renderer/layoutは移行期間中に戻せる状態に保ち、切替のために共有D1の設定を増やさない。表示設定をlocalStorageに保存する場合も、版付きキー・ログアウト時の扱い・旧版復帰を定義する。検証後に不要な旧CSS/DOM/イベントをまとめて撤去する。
