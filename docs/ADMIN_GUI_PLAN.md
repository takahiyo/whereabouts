# 管理GUI・メニュー再設計計画

更新: 2026-10-04。状態: 計画と独立試作あり、既存管理GUIへの統合は未実装。既存タブの順序・配置を引き継がず、管理者の作業単位から再構成する。[GUI刷新計画](GUI_REDESIGN_PLAN.md)の管理部分を本書で具体化する。GUI全体の優先度はP3を維持する。

進捗: 段階AとBの一部を[独立した操作試作](ADMIN_GUI_PROTOTYPE.md)として実装。メニュー、統合名簿、下書き、幅別配置を架空データで確認できる。既存管理画面への統合と共有APIへの編集接続は未実装。

## 設計の結論

管理画面を「メンバー・グループ」「お知らせ・予定」「ツール」「在席表の設定」「拠点・アクセス」の5領域に再編する。最初に開くのは「メンバー・グループ」。登録、編集、所属変更、表示順の変更を同じ画面で行い、名簿全体の変更を一つの保存単位として扱う。

管理は通常画面と同じアプリ内の専用画面にする。現在の大きな管理モーダルと、その中に開く登録モーダルの重なりを解消し、一覧と編集内容を見比べられるようにする。Vanilla JS構成を維持し、別アプリや新しいフレームワークは導入しない。見た目の再配置と保存仕様の変更は別々に実装する。

## 現状から解決する問題

| 他タブから名簿タブに戻る際に強制読込み | 未保存内容を失う経路がある | 領域ごとのdraftを保持し、再読込み・閉じる・拠点変更で明示確認 |
| グループ名クリックで名称編集、登録フォームの所属は自由入力 | 編集入口が隠れ、新グループが意図せず増えやすい | 明示的な「名称変更」、所属選択と「グループを追加」を分ける |
| deleteGroupは所属メンバーもdraftから削除 | グループだけ整理したい操作でも人員削除になる | 所属先の移動とメンバー削除を別操作にする |
| filteredMemberListは氏名検索。順番表示/ボタン判定は検索結果idx、moveMemberは全名簿の同一グループを移動 | 検索中に見えない相手との順序が変わり、表示番号も実順序と違う | 検索時は実際のグループ内順序を表示し、並び替えは全件表示の専用モードへ |
| buildMemberSavePayloadは人数0のグループを送らない | 空グループを追加して保存しても残らない | 初期は「下書きグループ」と明示し、最初のメンバー追加と一緒に保存 |
| handleMemberSaveは名簿設定と連絡先更新を別APIで処理 | 一部成功を単純な保存失敗として扱えない | 保存対象・成功範囲を見せ、後段で原子性/競合対策を整備 |

以上は現行コードに基づく。以下は改善後の仕様案であり、現行機能として案内しない。

## メニュー構成と既存機能の移動先

画面上部に「在席表へ戻る」「管理」「対象拠点」「現在の権限」を置く。対象拠点は編集フォーム内に散在させず、管理領域全体の文脈として常に表示する。拠点をまたぐ一括操作は初期対象外。

| 順序・主メニュー | 内部の作業 | 既存の移動元 |
|---|---|---|
| 1 メンバー・グループ | 全メンバー、グループ選択、登録/編集、所属変更、並び替え、CSV入出力 | グループ、メンバー、基本のCSV |
| 2 お知らせ・予定 | お知らせ一覧、予定一覧/カレンダー、関連お知らせ、休暇対象/期間 | お知らせ、イベント |
| 3 ツール | リンク一覧、登録/編集、表示順、リンク確認 | ツール |
| 4 在席表の設定 | 表示項目（列）、項目自動消去、印刷/出力 | カラム、基本の自動消去/印刷 |
| 5 拠点・アクセス | 拠点名、共有パスワード、権限説明。全体管理者のみ拠点一覧/追加 | 基本の拠点設定、拠点 |

「基本」「その他の設定」のような雑多な受け皿を作らない。「カラム」は「表示項目」、「イベント」は通常画面と共通の「予定」にする。用語だけで休暇固定等の業務仕様を変えない。内部API名は表示名に合わせて改名する必要はない。

「お知らせ・予定」は関連する情報の作業領域であり、内部に「お知らせ / 予定」の二つのビューを置く。予定から関連お知らせを選択/作成でき、一覧へ戻っても予定の入力は維持する。共通保存ボタンで両者を一括保存する仕様にはせず、対象名を付けた保存にする。既存API間にトランザクションがないため、関連作成の途中失敗は明示する。

CSV書出しは名簿の「CSV」入口から1操作で実行、取込みは「ファイル選択 → 検証 → 差分確認 → 適用」とする。印刷は通常画面の出力入口からも到達可能にし、利用者を管理設定に誘導しない。出力権限を拡張する場合は別途Worker側で確認する。

主メニューは全端末で同じ順序・名称を使う。各作業画面の「ヘルプ」から該当する説明を開く。権限がない管理入口は表示しない。表示制御で権限を代用せず、APIの既存認可を維持し、認可強化は後段で扱う。

## メンバー・グループの統合作業画面

```text
在席表へ戻る   管理   対象拠点: ○○   権限: ○○
主メニュー: メンバー・グループ / お知らせ・予定 / ツール / 在席表の設定 / 拠点・アクセス

メンバー・グループ                     [メンバーを追加] [グループを追加] [CSV]
[グループ一覧]          [検索・絞り込み] [並び替え]
 全メンバー (42)        選択グループ名・人数       [詳細/編集]
 営業 (12)              氏名 / 所属 / 連絡先       氏名
 開発 (30)              メンバー一覧               所属
 [グループ順を変更]     選択時: [所属を変更]        連絡先
                       グループ操作: [名称変更] [削除]

未保存: 追加2名・所属変更3名       [変更を確認] [変更を破棄] [名簿の変更を保存]
```

初期表示は全メンバー。グループは階層データではないため、初期設計では展開式ツリーにせず、人数付きの選択リストとする。全メンバーから横断検索でき、所属先を選ぶと絞り込める。検索対象は氏名・所属・内線を基本とし、携帯/メールは連絡先検索として選べる。結果件数、条件解除、該当なし、取得失敗を分けて表示する。

一覧の基本情報は氏名・所属・内線。携帯/メールなど長い情報は詳細にまとめ、PCでは必要に応じて一覧列にも表示できる。表示密度や列の選択はブラウザ内の設定とし、拠点共有の列設定と混ぜない。行のクリックは詳細表示、明示ボタンの「編集」で編集状態に移る。選択チェックは一括操作専用とし、行クリックで勝手に選択しない。

### 作業別の操作フロー

| 作業 | 操作順 | 意図を明確にする規則 |
|---|---|---|
| メンバー登録 | メンバーを追加 → 氏名/所属/連絡先 → 下書きに追加 → 必要なら続けて追加 → 名簿を保存 | 選択中グループを初期値にする。全メンバーでは所属選択必須。同姓同名を一律拒否せず識別IDを維持 |
| グループ作成 | グループを追加 → 名称 → 最初のメンバーを登録/移動 → 名簿を保存 | 空グループは下書きであると表示。永続化成功を先に通知しない |
| 個人の所属変更 | 詳細の所属 → 移動先選択 → 下書きに反映 → 保存 | IDと現在の在席・予定等を保持。新所属内では末尾に追加することを事前表示 |
| 複数人の所属変更 | チェックで選択 → 所属を変更 → 移動先/対象一覧を確認 → 下書きに反映 → 保存 | 対象件数を表示。移動者間の順序を保持して移動先末尾へ。検索/グループ変更で選択を解除し、非表示の人を操作しない |
| グループ順変更 | グループ順を変更 → 上下/位置指定またはドラッグ → 完了 → 保存 | 名簿のグループ表示順を変更する。メンバーの所属やグループ内順序は変更しない |
| メンバー順変更 | グループ選択 → 並び替え → 全メンバー表示で上下/位置指定/ドラッグ → 完了 → 保存 | 所属変更と分ける。他グループへドラッグ移動しない。「3/12」のようにグループ内順序を表示 |
| 名称変更 | グループ操作の名称変更 → 新名称 → 対象人数を確認 → 下書きに反映 → 保存 | 同名を禁止。所属人員を削除しない。新グループ追加と誤認させない |
| グループ削除 | グループ操作の削除 → 人数確認 → 所属先へ全員移動 → 空になったグループ削除 → 保存 | 人数がある場合は移動先必須。人員の同時削除はこの操作に含めない |
| メンバー削除 | 詳細または選択操作 → 氏名/所属/件数と予定への影響を確認 → 下書きから削除 → 保存 | グループ削除とは別操作。削除後の予定参照等は調査してから実装。曖昧な「整理」は使わない |
| CSV取込み | CSV → 取込み → 検証/既存との差分 → 下書きに反映 → 保存 | 置換対象と削除人数を明示。初期は既存の置換方式を維持し、マージ方式は別仕様として検討 |

並び替えはグループ名順/氏名順の一時的な閲覧ソートと分ける。「表示を氏名順にする」は保存順を変えない。検索中に「並び替え」を選んだ場合は検索解除を確認して、選択グループの全員を表示する。通常の絞り込み表示から隠れた相手との順序を変更させない。並び替えモードを閉じてもdraftに残ることを表示する。

グループ削除の移動先がない場合は、新しいグループを作ってから移動できる。最後のグループや全員削除は空名簿保存の扱いを後段で確定するまで実行不可とする。「未所属」の永続化や空グループ保持をGUIだけで新仕様として導入しない。

## 編集・保存の共通ルール

- 入力フォームの完了は「下書きに反映」、API成功は「保存しました」と区別する。未保存バッジと追加/変更/移動/削除件数を表示する。登録ボタン直後に保存済みと誤認させない。
- 名簿には一つの保存バーを置く。「グループを保存」「メンバーを保存」の二重入口はなくす。ほかの領域は保存対象を明記し、管理全体の一括保存ボタンは作らない。
- 保存前に差分を見られ、削除/置換時は対象一覧・件数の確認を必須にする。保存時はフォーム内の未反映入力も検出し、黙って除外しない。
- 主メニュー/グループの切替ではdraftを保持する。拠点変更・在席表へ戻る・再読込み・閉じるでは「保存 / 破棄 / 戻る」を提示する。ブラウザ終了時の警告は補助とし、終了後の復元を保証しない。
- 保存処理中は対象の二重送信を防ぐ。失敗時は入力と差分を保持し、再試行/破棄を選べるようにする。一部成功時に全体成功と表示しない。
- 競合時は新しい名簿と自分の差分を比較して再編集する。サーバーのbaseRev拒否を整備する前に「競合を防止できる」と案内しない。
- 初期の取消は保存前の下書き内に限定する。保存後の復元は履歴/権限付き取消の別開発（F10）として扱う。個人の連絡先をlocalStorageへ自動保存しない。

## 端末ごとの配置と共通操作

| 利用可能な幅 | 配置 | 共通性 |
|---|---|---|
| ワイドPC | 主ナビ、グループ、一覧、詳細を読める幅で同時表示。詳細の文字幅は制限 | 一覧を見ながら編集し、無駄に全幅へ引き延ばさない |
| 一般PC/iPad横 | 主ナビを省幅化。グループ+一覧を基本に詳細を隣接/置換表示 | 端末名ではなく実際の領域幅で切り替える |
| iPad縦/分割表示 | グループ選択を一覧上部に置き、一覧から詳細へ切替 | タッチでも同じ追加/移動/並び替えを提供 |
| スマートフォン | 主メニューを現在名付きのメニューボタンで開く。一覧/詳細を1画面ずつ表示 | 「戻る」で検索、グループ、スクロール位置を復元。編集内容は保持 |

管理メニューをスマホだけ別の分類や順序にしない。PCの常設ナビとスマホの開閉ナビは同じ項目を使う。ボトムに5管理項目を詰め込まず、通常画面のナビとも二重化させない。保存バーは画面下に配置し、ソフトウェアキーボードや拡大時に入力欄/フォーカスを覆わないよう実機で検証する。狭い画面の連絡先は詳細へ移すが、操作を削除しない。

上下ボタンと移動位置の指定を全端末で用意し、ドラッグは追加の操作方法とする。WCAG 2.2はドラッグ以外の単一ポインター操作とキーボード操作を求めるため、キーボード代替だけでは足りない。[W3CのDragging Movements解説](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)

タッチ操作の主要ボタンは44px程度を設計目標とする。WCAG 2.2 AAの対象サイズ基準は24×24 CSS pxまたは規定された例外であり、44pxをAAの必須値とは扱わない。[W3CのTarget Size解説](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)

## 実装順と共有D1への影響

本番・devは同じD1を使う仕様を維持する。devからの保存も本番データに作用するため、GUIだけの変更でも書込試験を先行実施しない。

| 段階 | 成果物/完了条件 | 影響と依存 |
|---|---|---|
| A 作業モデルと試作 | 本書のメニューと統合名簿を架空データで試作。PC/iPad/スマホで全作業を追える | devのみ。共有API接続/書込なし。GUI-01/02/05に含む |
| B 保存しないUI基盤 | 主ナビ、一覧/詳細、検索、グループ選択、幅適応、共通focus。書込操作はfixture内だけで検証 | 本番配信なし。既存API payload/権限/共有設定を変えない |
| C 保存基盤の保全 | 明日の予定保持（D01）、名簿保存の原子性（D02）、競合拒否（D03）、連絡先更新の部分成功/再試行を検証 | 後段。モックの障害/二端末試験を先に行い、共有資源の影響を別レビュー |
| D 管理編集の接続 | 統合draft/差分/保存、所属変更、削除防止、CSVプレビューを順に接続 | C完了後。共有試験拠点での確認は実施時に対象を限定。mainへの反映は別判断 |
| E 残る管理領域 | お知らせ・予定、ツール、表示項目、拠点・アクセスを同じ一覧/詳細方式へ | 各保存APIの失敗/認可/対象拠点を検証。一度に全APIを書き換えない |
| F 整理・移行 | マニュアルと用語/印刷を更新。代替画面の検証後に旧タブ/不要CSSを撤去 | GUI-06/M07。旧DOMを先に消して機能を失わない |

これはGUI-01〜06/U10/U11/F08等の具体化であり、独立の機能件数・人日を既存計画に加算しない。空グループの永続化、グループ固定ID、入れ子グループ、複数所属、削除後復元、監査ログ、管理権限の細分化は追加仕様候補。必要性と既存データ互換性を評価して別途採否を決める。

## 試作・受入れの確認項目

1. 初めて使う管理者が説明なしで「メンバー追加」「別グループへ移動」「グループと人員の順序変更」の入口を見つけられる。現状と試作で操作時間/迷った箇所/誤操作を比較する。
2. 全端末で同じメニュー名・順序・操作結果。幅変更、回転、分割表示、200%拡大で選択/入力/下書きが消えない。[GUI計画の幅別試験](GUI_REDESIGN_PLAN.md)を共用する。
3. 0/1/多数グループ、同姓同名、長い氏名、空グループdraft、検索結果0件/一部件、異なる所属の一括選択を確認する。
4. 検索中の順番と実順序が一致し、並び替えで非表示の人を意図せず動かさない。上下/位置指定/ドラッグの結果が一致し、キーボードと単純なタップで完遂できる。
5. メニュー切替・再読込み・拠点切替・管理終了で未保存内容が黙って破棄されない。保存失敗/競合/部分成功をfixturesで再現し、表示が実際の保存範囲と一致する。
6. グループ削除が人員削除にならない。登録/所属変更/並び替えの前後でIDと在席/時間/備考/勤務時間/明日の予定を保持する。予定のメンバー参照とCSVの互換性も確認する。
7. 各権限で到達可能な画面と操作を確認する。拠点切替後に前の拠点のdraftを新しい拠点へ保存できない。画面から隠した機能でもAPIの認可を確認する。

利用頻度による主メニュー順の妥当性と、一覧で常時見たい連絡先は試作で検証する。現在の利用頻度を実測した事実として扱わず、上記を初期案として進める。
