# 改善案と開発計画

作成: 2026-10-04（日本時間）。状態: devで段階実装中（共有D1への影響を避ける順序）。実装済みの整理内容は[コードレビュー](CODE_REVIEW_2026-10-04.md)で区別する。

## 目的・守る仕様

「今、誰がどこにいて、いつ戻り、どう連絡できるか」を拠点内で素早く共有する。付随する名簿、休暇・行事、お知らせ、業務リンクを同じ画面から扱う。利用者は一般スタッフ、拠点管理者、オーナー、全体管理者。共有端末と個人端末の両方を想定する。

本番・開発のD1共有はユーザー確認済みの仕様。WorkerとKVの分離を維持する。D1分離を計画に含めない。Vanilla JS、Cloudflare Pages / Workers / D1を継続し、GAS・Service Workerによるオフライン運用・全面的なフレームワーク移行を提案しない。開発ブランチは`dev`。mainに影響しない改善を先行し、共有D1・認証・保存・同期・Cronに関わる変更は影響を評価した後段で実施する。重大な指摘の優先度は保持し、着手順序とは区別する。

以下の工数は1人の実装・レビュー・検証を含む概算（S: 0.5–2人日、M: 3–5人日、L: 6–10人日）。外部サービスの契約、管理者同意、利用者検証待ちは別。実測前の仮説であり、全案の一括実装を推奨するものではない。

## 現在の技術・サービス動向との照合

2026-10-04に公式資料を確認した。以下は人気ランキングではなく、現行プラットフォームの仕様から導く採用判断。

| 根拠 | このアプリへの判断 |
|---|---|
| FirebaseはIDトークンの署名、issuer、audience、有効期限等の検証を要求 [S1] | 現行のpayload読取りのみの認証を最優先で置き換える |
| Workers KVは結果整合性で、即時反映や原子的な読み書き用途には制約がある [S2] | 在席の正はD1。保存直後の表示をKVの失効だけに依存させない |
| D1のbatchはトランザクションとして実行され、途中失敗はロールバックされる [S3] | 名簿の単独DELETEを見直す。共有DBで障害注入せずローカル検証する |
| WCAG 2.2は操作対象の大きさ・フォーカスの見え方を扱う [S4][S5] | 密度だけを優先せず、タッチ・キーボード・色以外の状態表示を受入基準にする |
| Google CalendarはsyncTokenによる差分同期と無効化時の再取得を提供 [S6] | 最初は予定の一方向取り込み。削除・再同期・重複抑止を初期設計に含める |
| Microsoft Graphは変更通知とsubscriptionによる連携を提供 [S7] | Outlook/Teams連携は通知の更新・検証・権限運用まで一機能として見積もる |
| Slack Web APIにはレート制限と429への対処が必要 [S8] | 個々の在席更新を無制限に通知せず、購読・集約・再試行を設ける |

AIによる自動在席推定より、手動更新の速さ、鮮度の明示、予定連携の信頼性を優先する。AIは任意の文章下書き等に限定し、本人確認なしの状態変更や従業員評価へ広げない。

## GUI刷新の位置づけ

ユーザー追加要件: ワイドPC、iPad、スマートフォンを対象に、幅を活かした表示と共通の操作感覚を設計する。レスポンシブ表示とメニュー/リスト刷新を一つの計画にまとめ、優先度は低い（P3）とする。

詳細は[GUI刷新・端末適応計画](GUI_REDESIGN_PLAN.md)。グループの配置数と一覧/カード形式を独立させ、1グループでも幅があれば一覧を使えるようにする。全端末で「在席 / 予定 / お知らせ / ツール」の名称と順序を共有する。固定した端末判定より実際のコンテナ幅を使い、iPadの回転・分割表示も検証する。

管理GUIは[管理メニュー再設計計画](ADMIN_GUI_PLAN.md)の「メンバー・グループ / お知らせ・予定 / ツール / 在席表の設定 / 拠点・アクセス」の5領域とする。既存の8タブや以前の4分類案を前提にしない。登録・所属変更・並び替えを統合名簿画面で完結させ、保存する対象を明示する。

GUI刷新が未着手でも、既存画面のfocus復帰・読みやすさ・状態表示等の局所的な改善は先行できる。共有D1の列設定を書き換える実装はGUI試作に含めない。統合管理の編集/保存を接続する段階はD01/D02/D03と部分成功の検証後とし、書込なしの試作と分ける。

## 外部連携の共通設計

カレンダー連携は空き/予定あり等の最小情報から開始し、件名・参加者・休暇理由は初期状態で取り込まない。連携トークンはフロントのlocalStorageや通常ログに保存せず、Worker側でアクセス権限を限定して暗号化保存する。暗号鍵はSecretで管理し、連携解除時は失効・削除する。必要scopeと組織管理者同意、利用プラン、API制限はPoC時に再確認する。

データモデル候補: integration_connections、external_event_mappings、sync_cursors、notification_deliveries、audit_events。全てoffice_idを持ち、個人連携ではmember/userとの対応も持つ。外部IDと連携元で重複抑止し、手動変更の有効期限を優先する。通知と主操作の保存を切り離し、連携先停止中も在席更新を継続する。

最初の連携は、実利用がGoogle Workspace中心ならI01、Microsoft 365中心ならI02のどちらか一つ。二つを同時に始めない。利用組織・契約状況は未確認のため、ここは採否判断事項として残す。
